# CCSwitch 聚合模式能探测什么

聚合模式可接入本工具。CCSwitch 根据客户端选中的模型条目分发请求，`ccs-` 前缀用于区分供应商和模型；普通模型请求由默认供应商承接。探测器放在同一个本地入口前：

```text
Codex → 探测器（18741）→ CCSwitch（实际发现的端口）→ 所选供应商
```

## 能看到的证据

| 内容 | 观测条件与含义 |
| --- | --- |
| 请求模型 / 路由标签 | 请求经过探测器且报文可解析时记录；标签表示客户端选择，不认证最终出站来源 |
| 请求思考强度 | 读取实际请求的 `reasoning.effort` 等字段；未指定时不拿配置默认值填充 |
| 返回模型 / 最终强度回显 | 读取 CCSwitch 交付的完整最终响应；缺失、null、冲突分别展示 |
| CCSwitch 转换后的出站强度 | 当前观测点看不到；不能从客户端请求直接推定 |
| 模型内部真实强度 / 算力 | 协议字段不能证明，回显一致也不是算力验证 |

## 为什么可能一直显示未回显

供应商原生 Responses 接口只有在最终响应保留强度字段时才能比较。供应商改用 Chat Completions 或 Anthropic Messages 接口时，CCSwitch 会转换协议。核对的源码中，两种流式转换器的 `base_response` 构造了模型、状态、输出和用量，没有添加 `reasoning.effort` 或 `reasoning_effort`。因此，这两条转换路径的最终强度可能不可核验，即使回答包含思考内容。

CCSwitch 也会映射请求参数。例如 Chat 转换配置使用 `openrouter` 档位模式时，`max` / `ultra` 会映射成 `xhigh`；Anthropic 转换会按模型和历史状态选择 `output_config.effort`、adaptive thinking 或 thinking token 预算。这些是适配规则，不能把不同协议的字符串差异直接判成服务商偷偷降低思考强度。本工具不会根据源码规则填入“实测出站值”。

思考 tokens 也只是交付报文中的用量声明；转换器可能为缺失用量补零。0、缺失或回答有无思考正文，都不能代替强度回显。

## 操作

保持 CCSwitch 的“聚合生效中”，双击本目录的 `一键启用.cmd`。等待当前任务完成后彻底退出并重新打开 Codex，然后照常使用。模型切换仍在 Codex 中进行。探测器不会自动为每家来源发送测试请求。

如果面板没有真实记录，先确认 Codex 已重新加载地址；同时查看面板接入状态。CCSwitch 退出、切换运行模式或重写配置后，原有接入可能失效。它恢复到本地聚合入口并正常工作后，可以再次使用一键入口接入；不要在接入瞬间同时编辑配置。
