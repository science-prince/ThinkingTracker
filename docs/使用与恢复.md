# 使用、恢复和故障排查

## 第一次启动

先确认 CCSwitch 的 Codex 代理已开启、原来的 Codex 能正常使用。双击 `一键启用.cmd`，看到“观测已启用”后重新打开 Codex，再正常发送消息。

程序默认用 Node 22+；本机已经有 Node 24。Python 只使用已经配置好的 Anaconda `selfcontrol`，不安装其他依赖。入口会在后台启动服务，再打开浏览器。首次浏览器打开可能稍有延迟，面板会继续更新接入状态。

希望先体验时，双击 `模拟演示.cmd`。它不读真实 Codex 配置，不连真实 CCSwitch 端口，四条记录都带模拟标记。真实面板正在运行时，先停止再开启隔离演示。演示或只读面板运行时，双击“一键启用”会安全停止旧面板，然后启动真实接入模式。

## 日常观察

正常通过 Codex 发消息即可。工具本身不发送“测谎题”、不主动向服务商发探测请求、不改变模型或强度。首次启用只做本机 TCP 连通检查，用来确认 CCSwitch 在监听。

“请求强度”来自实际发来的请求；界面不把 `model_reasoning_effort` 的默认配置视作已发送的协议证据。“首包回显”来自第一个包含相关元数据的响应快照，“最终回显”来自结束事件或完整 JSON；二者不同会在详情标出 `first_final_echo_changed`。

模型路由前缀可能被 CCSwitch 去掉，例如请求 `provider-a/gpt-demo`、响应 `gpt-demo`。程序分别保留两者，不把这种命名差异直接定性为“偷换模型”。没有实际出站证据时，来源列只是请求端路由标签。

关闭面板网页只会关掉网页，后台服务仍转发。没有系统自启动注册，重启电脑后需再次双击启动；异常退出后需恢复地址。

## 正常停止

平稳操作顺序：

1. 面板点击“恢复地址”。
2. 重新打开 Codex，让新进程读取恢复后的原地址；此前已在途的请求继续完成。
3. 双击 `停止并恢复.cmd`，或点击“恢复并停止”。

也可以直接双击停止入口，再重新打开 Codex。进程会等待正在进行的请求结束，不会自动强杀 Codex 或 CCSwitch。WebSocket 的空闲连接随后关闭。长期不结束的请求可能使停止延后；默认空闲超时 5 分钟。

若停止时报告恢复失败，转发服务会继续运行，避免配置还指向已关闭端口。查看错误，解决配置路径或权限问题后再次恢复。

## 异常退出或断电

双击 `紧急恢复地址.cmd`。它直接读取 `data/recovery.json`，即使没有运行中的面板也能恢复。此操作不会安装软件、强杀其他进程或写 CCSwitch 数据库。

恢复记录的格式示例（这是模拟地址）：

```json
{
  "version": 1,
  "config_path": "C:/Users/你的用户名/.codex/config.toml",
  "entries": [
    {
      "keys": ["openai_base_url"],
      "old": "http://127.0.0.1:15721/v1",
      "new": "http://127.0.0.1:18741/v1"
    }
  ]
}
```

只有当前值仍等于 `new` 的字段会恢复成 `old`。若当前值已被你改成别的地址，会保留它并计入“跳过”。字段级恢复不会用整份旧配置覆盖你的新设置。

如果 Node / Anaconda 已损坏，导致紧急恢复入口也不能运行，可用文本编辑器打开恢复记录里的 `config_path`，找到 `keys` 指定的字段：例如 `openai_base_url`，或 `[model_providers.custom]` 下的 `base_url`。确认当前值等于 `new` 后，改回 `old`，保存并重新打开 Codex。只编辑这些地址，不要修改认证、模型、hooks 等其他内容。地址复原后，可在 CCSwitch 重新应用对应配置。

## 常见问题

| 问题 | 处理 |
| --- | --- |
| “未发现 CCSwitch 本机代理” | 在 CCSwitch 开启 Codex 代理；确认 Codex 配置里的地址确实指向它；再启用 |
| “CCSwitch 没有监听” | 启动 CCSwitch 并开启代理。连通检查失败时工具不会接入 |
| 端口占用 | 先检查是否已有本工具在运行；正常停止后，修改 `设置.json` 的两个端口，再启用 |
| 启用后没有记录 | 重启 Codex；检查是否用了其他 profile、命令行地址覆盖或直接远端连接 |
| 切换来源后状态变成未接入 | CCSwitch 可能重新写回了 Codex 地址；再次启用观测并重启 Codex，程序不会后台抢写 |
| 只有首包值，没有最终值 | 上游最终未回显或请求未完整结束；无法据此核验强度 |
| 显示 null / 未回显 | 服务商没有可比较的返回字段；这不证明它降低了强度 |
| “关联不确定” | WebSocket 请求重叠且不能可靠关联；不会猜测哪条响应属于哪条请求 |
| “无法解析” | 看详情的 warnings；可能是压缩 WebSocket、二进制消息、未知编码、异常 JSON 或超过观测上限 |
| 停止后 Codex 连不上 | 旧进程仍缓存探测器地址；运行紧急恢复入口并重新打开 Codex |
| 打开网页但提示令牌无效 | 用双击入口重新打开，不要复制旧的带令牌链接给其他人 |
| 配置使用特殊 TOML 写法 | 自动接入只支持普通单行 URL 赋值；内联表、多行字符串等不猜测改写，按恢复记录与配置说明手动调整 |
| 历史记录损坏或磁盘不可写 | 原文件不会被自动删除或覆盖；没有请求在进行时可主动清空记录，或停止后另行保留损坏文件 |

## 可选设置

一般无需改设置。如果配置并非默认位置，可在 `设置.json` 增加 `codex_config_path` 与 `ccswitch_db_path` 两个绝对路径。Windows JSON 路径推荐使用 `/`，例如 `E:/自定义目录/config.toml`。Python 路径应指向本机 Anaconda 的 `envs/selfcontrol/python.exe`，实际环境名称须为 selfcontrol。

`max_records` 允许 10–2000；`max_inspect_bytes` 允许 64 KiB–16 MiB；`idle_timeout_ms` 允许 10 秒–30 分钟。增大观测上限会增加内存使用。端口只接受 1024–65535 的整数，面板和代理端口不能相同。程序没有允许公网监听的设置。

修改设置、移动目录或删除 `data/` 前，先恢复地址并正常停止。尤其不要在仍接入时修改代理端口，否则 Codex 可能继续指向旧端口。
